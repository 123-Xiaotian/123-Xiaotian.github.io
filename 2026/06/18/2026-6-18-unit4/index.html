Unit4 正向建模与图书馆管理系统

一、正向建模与两阶类图

Unit4 的核心实践是正向建模：先画 UML，再写代码，而非从代码反向生成 UML。本单元的三次作业（hw13/hw14/hw15）围绕图书馆管理系统逐次扩展，UML 模型从第一版设计开始就被要求以”两阶类图”提交——第一次提交初版设计模型，第二次提交最终代码对应的实现模型。

两阶类图的作用

两阶类图的机制迫使开发者在编码前完成架构决策，而非在代码中”边写边想”。具体来说：

  • 阶段一（设计类图）：确定有哪些类、每个类有哪些属性和方法、类之间的关联关系。这一步要求开发者从需求文档中提取领域模型，而不是面向具体 API 做设计。例如 hw13 初期，我确定了 LibraryManager 作为总调度器、BookShelf/BorrowReturnOffice/AppointmentOffice 作为三个物理场所的抽象、Book 和 User 作为核心实体。这些类的职责边界在设计阶段就被锁定——借还处只管暂存，预约处只管预约，书架只管存书——后续迭代中从未因职责不清而需要重构。

  • 阶段二（实现类图）：编码完成后，将实际代码的类结构同步回 UML。这一步暴露出设计阶段没有预料到的细节。例如 hw14 新增 TreasuredBookShelf 后，我发现需要在 LibraryManager 中新增 isTreasured() 和 moveToCorrectShelf() 方法，并在模型层补上相应的关联线和属性。两阶对比的过程本身就是一次架构审查。

设计类图决定”做什么”，实现类图验证”怎么做”是否与”做什么”一致。

正向建模与反向建模的对比

与 Unit1-3 先写代码后补图的做法相比，正向建模最显著的差异是：bug 的产生模式变了。反向建模时代，bug 往往是”代码逻辑写错了”；正向建模时代，bug 更多是”设计模型与实现模型之间的不一致”——例如 UML 中声明了关联但代码中没有对应的字段引用（R2 评测失败），或者方法名在代码中改了但 UML 没同步（R3 评测失败）。这种 bug 的根源在于设计与实现的脱节，而非逻辑本身的错误。

二、架构设计与 UML 模型追踪

最终代码架构

hw15 的最终代码由 16 个类构成，分为三个层次：

  • 实体层：Book、User、DueEntry、Reservation、OrderRequest、ReadingEntry、ScoreRecord
  • 场所层：BookShelf、TreasuredBookShelf、BorrowReturnOffice、AppointmentOffice、ReadingRoom
  • 调度层：LibraryManager、MainClass、DueTracker、GradeCalculator

LibraryManager 持有所有场所和追踪器的引用，方法按操作类型命名（handleBorrowBook、handleReturnBook 等），arrangeBooks 负责整理逻辑。DueTracker 采用 38 槽循环数组 + head 指针的设计，按日历差自动前进，支持跳过无指令日期的场景。整个数据流是单向的：MainClass 读指令 → LibraryManager 调度 → 各场所执行 → PRINTER 输出。

代码与 UML 模型的追踪关系

StarUML 的 .mdj 文件本质上是 JSON。实现类图（uml_ultimate.mdj）包含 19 个 UMLClass 元素（16 个业务类 + 3 个内部属性的类引用）和 15 条 UMLAssociation。以下是对应关系的关键点：

代码元素 UML 对应 追踪方式
LibraryManager 的 10 个字段 10 条 UMLAssociation 指向对应类 end1/end2 的 $ref 指向双方类的 _id
DueTracker.buckets 数组字段 属性列表中的 UMLAttribute type 字段设为 List[]
handleBorrowBook 方法 UMLOperation + @Trigger 注解 操作名完全一致，参数类型匹配指导书要求
顺序图 4 条消息 UMLSequenceDiagram 中的 UMLLifeline + UMLMessage 每条 lifeline 的 represent 同时含 _type: "UMLClass" 和 $ref

主要的追踪不匹配出现在：

  • 空壳方法：Book.getBookCopyId()、Book.getBookCategory()、AppointmentOffice.orderBook() 等在代码中不参与任何业务逻辑，但为了通过 R2/R3 评测必须同时存在于代码和 UML 中。这些方法是评测驱动的产物，不是设计意图的体现。
  • 内部类拉平：ReadingEntry 和 DueEntry 原本设计为内部类，但 UML 评测不认内部类，必须拉平为独立的顶层 UMLClass。代码中的内部类变成平级类后，关联关系需要重新建立（ReadingRoom → ReadingEntry、DueTracker → DueEntry）。
  • StarUML 重保存丢视图层：程序化插入的 ownedViews（UMLClassView、UMLAssociationView）在 StarUML 打开顺序图后直接保存会丢失。这使得”先代码后同步 UML”的工作流不可靠——必须用脚本一次性生成所有视图层数据。

hw14 → hw15 架构扩展分析

从 hw14 到 hw15，新增了信用分系统、借阅期限和续订三大功能。架构上的变化：

  • DueTracker 类的引入是本次迭代中最关键的架构决策。如果直接在 LibraryManager 中维护 HashMap<bookId, dueDate>，虽然简单，但 tick 操作需要遍历所有在借书判断逾期——O(n) 每 tick。而循环数组方案将 tick 降为 O(过期数)，且天然处理日期跳空场景。
  • User 类新增 creditScore 字段和 addCredit(delta) 方法，信用分检查嵌入到 handleBorrowBook、handleOrderBook、handleReadBook 的拒绝条件中。这种”分散式权限检查”是权衡后的选择——如果抽象出一个 CreditChecker 类，虽然内聚性更好，但对于仅 3 处调用且逻辑简单（> 80、> 40、> 0）的场景，增加新类的收益不足以抵消 UML 图同步的额外工作。
  • arrangeBooks 的 tick 调用位置经历了一次修正：最初放在闭馆整理中单独调用，后改为每次 arrangeBooks 开头统一调用，不分开闭馆。这一改动因为 tick 按日历差前进，不需要区分开闭馆——逾期就是逾期，在任何整理时机都应该处理。

三、大模型辅助正向建模

本单元中，我深度使用了 Code Agent（主要为 hermes + deepseek-v4-pro）辅助架构设计和 UML 同步。以下是实际使用总结。

任务分工

我将 Agent 定位为”架构评审员”和”UML 同步工具”，而非”架构设计师”。具体角色：

  • 我：阅读指导书、确定类职责划分、设计核心数据结构（如 DueTracker 环形数组）、编写业务逻辑
  • Agent：审查架构一致性（UML 与代码的差异检测）、检查顺序图 R1-R4 合规性、在迭代中对比新旧 jar 包 API 变化

引导大模型完成架构设计任务的方法

通过三次迭代的反复使用，我总结出以下有效引导策略：

  1. 先给约束再给任务：直接把指导书 pdf 扔给模型让它”设计架构”会得到一份过度抽象或脱离 API 的方案。正确的做法是先明确硬约束——“官方包 library3 提供了这些类，你必须基于这些 API 设计”——然后再问架构问题。约束包括：不可修改的接口、PRINTER 的调用规则、状态转移必须标注 @Trigger。

  2. 要求维护”设计决策日志”：每当我做出一个架构决策（如”DueTracker 用循环数组而非 HashMap+遍历”），让 Agent 记录决策理由、替代方案和取舍。在后续迭代中，当新需求到来时，Agent 可以自动检查既有决策是否与新需求冲突。例如续订功能的引入对 DueTracker 的影响——Agent 在日志中发现”SLOTS=31 是基于 C 类 30 天最大值”这一决策，立即指出续订 +7 天后需要扩容到 38。

  3. 分步验证，不一次到位：对于顺序图这种 StarUML 格式极其敏感的任务，让 Agent 分四步走：(a) 生成 .mdj 的 JSON 结构描述 → (b) 人工确认节点和消息是否正确 → (c) 程序化写入 → (d) 用独立 Python 脚本逐条校验 R1-R4。如果没有步骤 (d) 的独立校验，仅凭 StarUML 视觉检查很容易漏掉 end1/end2 格式错误或 represent._type 缺失。

  4. 让模型”解释而非决策”：对于架构权衡（如”是否将信用分检查抽象为 CreditChecker 类”），不让模型直接选方案，而是要求它列出两个方案的优势、劣势和在当前约束下的适配性。最终决策仍由我做出，但模型的对比分析让我更快地看到盲区。

大模型的局限性

  • 忽视评测规则：Agent 给的 UML 方案经常出现内部类，但实际评测不认内部类。这类课程特有的约束（不是 Java 语言的约束，而是评测系统的约束）模型无法从通用知识中推导，必须由我手动纠正。
  • StarUML 格式细节盲区：Agent 生成的关联使用 ends 数组而非 StarUML 原生格式的 end1/end2，导致重保存后丢失。这种工具级别的细节差异，模型往往在多次试错后才能”记住”——这也是为什么我把它固化为技能而非每次重新指导。
  • 过度设计倾向：Agent 曾建议引入 CreditPolicy 接口 + DefaultCreditPolicy/PremiumCreditPolicy 实现，用于未来的策略扩展。但在一个仅需三种阈值判断（>80、>40、>0）且迭代终点已知的场景中，这种抽象纯粹增加 UML 同步负担和 checkstyle 风险。

实践流程总结

  1. 用 Agent 做 API diff：新旧 jar 包的 javap 输出对比，列出所有新增/删除的方法和类
  2. 人工确定架构决策后，让 Agent 审查是否与既有设计原则一致
  3. Agent 生成 .mdj 修改脚本，人工跑一遍验证 StarUML 打开不丢失数据
  4. 独立校验脚本检查 R1-R4，Agent 辅助解读失败点并给出修复方案

四、四个单元架构设计思维的演进

回顾整个 2026 OO 课程，四个单元的架构设计思维呈现出明显的演进轨迹：

Unit1：语法驱动，分层解耦

第一次作业就确立了 AST 解析前端与底层代数引擎分离的核心架构。Lexer → Parser → Expr/Term/Factor → Poly 的单向链路，使得后续两次迭代（括号嵌套、求导算子）可以在不重构的前提下完成。这一单元的思维核心是”把变化隔离在边界之内”——预见到需求会变（新增因子类型），所以用 Factor 接口和 toPoly() 方法抽象了解析与计算的边界。

但问题也很明显：Poly 和 Parser 的耦合度达到全局最高的 12，Poly 类的响应数量高达 64。这说明我在追求功能可扩展性的同时，忽略了类的职责单一性。

Unit2：并发驱动，状态机建模

电梯调度是并发编程的第一课。这一单元的架构思维从”对象关系”转向了”线程交互”。核心发现：在多线程系统中，类的职责划分不仅取决于业务逻辑，更取决于锁的粒度。Strategy 被设计为无状态纯函数（不持有任何锁），WaitQueue 封装了所有 wait/notify 同步细节——这种”有锁的归信箱，无锁的归策略”的分层，是我在架构思维上最大的进步。

Unit3：规格驱动，接口契约

JML 单元的核心变化是从”我设计接口”转向”接口由规格给出”。架构设计的自由度被大幅压缩——类名、方法签名、异常类型全部由 JML 锁定。这一单元教会了我一件事：当接口被外部规格锁死时，架构设计的重心从”定义接口”转向了”优化实现”——选择 HashMap 还是 ArrayList、缓存哪些中间结果、如何组织内部辅助方法——这些是规格不限制的部分，也是人与人之间性能差异的来源。

Unit4：模型驱动，正向设计

第四单元是前三单元的反转：不再是先写代码再补 UML，而是先画类图再写代码。两阶类图的机制让我第一次体验到”设计先行”的完整流程。最大的感受是：正向建模不会减少编码工作量——事实上，同步 UML 的过程往往比写业务逻辑更耗时——但它显著减少了”因为设计缺陷导致的重构”。hw13 到 hw15 的三次迭代中，核心类（LibraryManager、Book、User）的关系模型从未改变，新增的类都是”追加”而非”修改”。

整体演进趋势

  • 从关注”功能实现”（Unit1）到关注”职责边界”（Unit2）
  • 从关注”接口设计”（Unit3）到关注”设计与实现的追踪关系”（Unit4）
  • 从”代码即设计”到”设计先于代码”到”模型约束代码”

五、四个单元测试思维的演进

Unit1：功能测试 + 互测对抗

测试手段主要是构造边界数据和复杂嵌套表达式，通过评测机批量对比输出。测试思维停留在”覆盖指导书规定的所有语法结构”层面。互测环节关注他人代码的架构缺陷——如果对方用全局字符串替换处理自定义函数，就构造深层嵌套的选择因子诱发 TLE。

核心教训：测试数据的构造需要理解被测代码的实现方式，而非仅仅理解需求文档。

Unit2：并发测试 + 时序推演

多线程 bugs 无法通过常规的功能测试复现。这单元我学会了”构造恶意时序”——利用睡眠间隙（sleep(400)）、TOCTOU 窗口和惊群效应来触发竞态条件。测试从”输入→输出”的静态验证转向了”输入→中间状态→输出”的动态验证。

核心教训：并发测试的本质不是覆盖分支，而是覆盖线程交织的可能性空间。即使分支覆盖率 100%，一个 notifyAll 的位置偏移也可能导致 RTLE。

Unit3：规格测试 + 快照全接口覆盖

JML 单元的测试具备了一个关键特征：可验证性来自规格而非预期结果。ensures 子句可以直接翻译为 JUnit 断言，assignable \nothing 要求对所有可观察状态打快照并逐字段比对。这一单元的测试思维从”验证正确性”转向了”验证合规性”。

核心教训：assignable \nothing 的快照必须覆盖接口暴露的每一个 getter，不能只覆盖”看着会变”的字段。hw11 的 recommendNthUp 测试中，followers、medals、hasReceived、influences 等 14 个维度的遗漏都是在多轮修正后才补齐的。

Unit4：评测驱动 + 一致性测试

Unit4 的测试不是传统意义上的 JUnit，而是评测系统的 R1-R4 规则。R2 检查 UML 与代码的类和方法是否一致，R3 检查状态图/顺序图中的消息是否有对应方法实现。这种”评测即测试”的模式对我的测试思维产生了新的影响：测试变得自动化但反馈周期变长（需要提交才能看到结果）。

核心教训：评测规则本身也是”需求”的一部分。内部类 UML 不通过、end1/end2 格式错误这些问题，在传统的单元测试思维中不会被关注，但在模型驱动开发中是实实在在的 bugs。

整体演进趋势

  • 从”验证功能”到”验证合规”（Unit1 → Unit3）
  • 从”预期驱动”到”规格驱动”（Unit1/2 → Unit3）
  • 从”静态验证”到”动态时序验证”再到”一致性验证”（Unit2 → Unit3 → Unit4）
  • 测试的范围逐步从”代码逻辑”扩展到”接口契约”再到”模型一致性”

六、课程收获

回看这四个单元，OO 课程提供了一条完整的设计能力提升路径：

表现：在课程开始前，我的编程思维是以”函数”和”过程”为中心的，类的存在更多是为了组织代码文件而非体现设计意图。

原因：之前的编程经验主要集中在算法竞赛和小型脚本，缺乏对大规模、多迭代、有并发需求系统的设计训练。

教训：经过四个月、四个单元、十二次作业的迭代，我收获了几条将长期影响我编程习惯的原则：

  1. 边界比实现重要。Unit1 的 Factor 接口和 Unit2 的 Strategy 无状态类说明，好的设计不是写最多的代码，而是在正确的地方画边界。边界一旦确立，内部实现可以自由迭代。

  2. 约束是设计工具，不是限制。JML 的 assignable 和 UM的 @Trigger 看似是额外负担，但实际上是强制开发者回答”谁会改这个状态”、”状态如何转移”这两个核心设计问题。没有约束的自由设计往往导致职责散落。

  3. 评测驱动不等于测试思维。Unit4 的 R1-R4 评测教会我，在特定领域（如模型驱动开发），”通过评测”和”设计正确”是不完全等价的概念。评测覆盖不了架构质量，但可以驱动架构的精细化。

  4. Agent 是放大镜，不是替代品。四个单元中，我越来越清楚地意识到：Agent 最不可替代的价值是”速度和不会疲劳”——它在 diff 对比、UML 一致性检查、API 变更检测上的效率远超人工。但架构决策的最终责任在开发者——Agent 可以列出方案的利弊，但无法理解课程约束、无法预测未来的迭代方向、无法判断一个抽象是否”过度”。

  5. 测试是设计的镜子。如果一个测试很难写，往往说明架构有问题——要么是职责边界不清导致需要 mock 太多依赖，要么是可观察状态暴露不足导致无法做 assignable nothing 验证。反过来，好的设计天然容易测试。

感谢老师和助教一个学期的付出，感谢互测中相互”折磨”的同学们。OO 课程的结束不是面向对象思维的终点，而是用这种思维去看待每一个软件系统的起点。
