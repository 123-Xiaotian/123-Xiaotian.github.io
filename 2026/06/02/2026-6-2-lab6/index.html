思考题

Thinking 6.1

不关闭不会用到的管道端会导致进程永远阻塞。

以读者为例：读者期望在管道为空、写端已关闭时读到 EOF 并退出。但如果读者自己没有关闭写端，那么 pageref(wfd) 永远不会为 0，_pipe_is_closed 永远返回 0。读者每次检查都会认为”写者还在”，于是 syscall_yield() 让出 CPU，醒来后再检查、再 yield，进入死循环。写者端同理。

实质原因：恒等式 pageref(rfd) + pageref(wfd) = pageref(pipe) 要求两端引用都正确反映，多出来的未关闭 fd 破坏了等式语义。

Thinking 6.2

只需交换父子进程中 close 和 read/write 的操作对象：子进程关闭 p[0]（读端），操作 p[1]（写端）；父进程关闭 p[1]（写端），操作 p[0]（读端）。

修改后关键代码：

管道本身不区分”谁写谁读”，只区分 fd 的只读/只写模式。父子双方各自关掉自己不用的那端即可。

Thinking 6.3

PIPE_SIZE 过小（32 字节）的影响：

吞吐方面：每次 syscall_yield 切换后只能传输少量字节（最多 32），然后必须再次让出 CPU 等待对方消费或生产。大量数据传输时，进程在读写-yield 之间频繁振荡，有效吞吐远低于物理内存带宽。

切换效率：缓冲区越小，读者和写者”填满 / 清空”的速度越快，触发 yield 的频率越高。每次 yield 意味着一次完整的上下文切换（保存/恢复寄存器、TLB 刷新等），开销固定但频率随 PIPE_SIZE 减小而急剧上升。极限情况下，每传输 1 字节就要切换一次，CPU 大部分时间花在调度而非数据传输上。

PIPE_SIZE 设置为 32 是故意的——用于触发竞态条件方便测试。

Thinking 6.4

恒等式 pageref(rfd) + pageref(wfd) = pageref(pipe) 并不在所有时刻成立。

不成立的两个典型时刻：

  • pipe_close 执行到一半时：如果先 unmap pipe 再 unmap fd，在两个系统调用之间 pipe 的 pp_ref 已经减 1 而 fd 的还没减，此时 pageref(rfd) + pageref(wfd) > pageref(pipe)。
  • dup 执行到一半时：如果先 map fd 再 map pipe 数据页，fd 的 pp_ref 已加 1 而 pipe 的还没加，此时 pageref(fd) > pageref(pipe)。

会否造成误判：会。比如在 pipe_close 先 unmap pipe 后 unmap fd 的间隙，若发生进程切换，另一进程调用 _pipe_is_closed 可能观察到 pageref(fd) == pageref(pipe)（因为 pipe 引用已减），从而误判”对端已关闭”，导致读者提前读到 EOF 或写者提前返回。

Thinking 6.5

dup 中的竞争场景（假设复制一个管道读端 fd）：

进程 A 调用 dup(oldfd, newfd)，它先 close(newfdnum)，然后 map fd 页面（syscall_mem_map(0, oldfd, 0, newfd, ...)）。此时 pageref(rfd) 从 1 变为 2。

在 map fd 之后、map 数据页之前，时钟中断发生，切换到进程 B。进程 B 正在管道读端上执行 _pipe_is_closed，它读到 pageref(fd) = 2，pageref(pipe) 可能为 2（因为 pipe 数据页的引用还没被 dup 增加）。此时 pageref(fd) == pageref(pipe) 成立，进程 B 误判写端已关闭，错误退出。

根因：close 和 dup 都是”先 fd 后 pipe”（或相反），不是原子的两步操作，进程调度可能插入其间。

Thinking 6.6

MOS 中并非所有系统调用都是原子操作。系统调用的”原子性”仅指单条 syscall 指令本身在内核态执行期间不会被中断——内核在 exc_gen_entry 中设置了 Status 寄存器的 EXL 位，关闭了中断响应。

但用户态函数（如 fork、pipe_close）即使其内部每条 syscall_* 是原子的，多次系统调用之间仍然可能被时钟中断打断。反例：

pipe_close 包含两次 syscall_mem_unmap：unmap pipe 数据页和 unmap fd 页。两次调用各自是原子的，但两者之间的间隙可以被调度。这恰恰是 Thinking 6.4/6.5/6.7 讨论的竞态根因。

代码证据：kern/genex.S 中 exc_gen_entry 设置了 Status_EXL，保证了单次异常处理不被嵌套中断打断。但返回用户态后 EXL 清零，时钟中断随时可以发生。

Thinking 6.7

第一条：控制 pipe_close 中 unmap 顺序可以解决问题。

分析：原顺序是先 unmap pipe 再 unmap fd。在两个 unmap 间隙，pipe 的 pp_ref 减 1 而 fd 未减，可能导致 pageref(fd) == pageref(pipe)。改为先 unmap fd 再 unmap pipe 后，fd 的 pp_ref 先减。在间隙中 pageref(pipe) > pageref(fd) 始终成立，不会触发误判”对端关闭”。

但仅靠 swap 顺序不能完全解决问题——它只解决了”写”的同步（pp_ref 的递减顺序），没有解决”读”的同步。进程可能在两次 pageref 读取之间被切换，读到脏数据。这需要 env->env_runs 机制来保证（Exercise 6.1 的 _pipe_is_closed 实现）。

第二条：dup 存在镜像问题。

dup 操作使 pp_ref 递增而非递减。如果先 map fd 再 map pipe，间隙中 pageref(fd) 已增而 pageref(pipe) 未增，也可能导致 pageref(fd) == pageref(pipe) 的误判。修复方法对称：先 map 数据页（增加 pipe 引用），再 map fd 页（增加 fd 引用）。

Thinking 6.8

问题一：打开文件的过程

open(path, mode) 在 user/lib/file.c 中实现。流程为：分配一个 fd（fd_alloc），构造 fsipc_open 的 IPC 请求发给文件系统服务进程 fs_serv。fs_serv 在内核的 serve_open 中查找路径对应的 struct File，分配一个内部 file id，将 File 结构和磁盘块映射回用户进程的 fd 数据区。之后用户态通过 fd2data(fd) 就能直接读写文件数据。

问题二：读取并加载 ELF 文件

Lab3 中 load_icode 在内核态通过 elf_from 解析 ELF 头，ELF_FOREACH_PHDR_OFF 遍历程序头，elf_load_seg 借助 load_icode_mapper 分配物理页并拷贝段内容。Lab6 的 spawn 在用户态完成类似流程：用 open + readn 读取 ELF 头和程序头（而非直接访问内核地址），用 read_map 获取文件数据页的映射，用 spawn_mapper（回调）借助 syscall_mem_alloc + syscall_mem_map 为子进程分配并填充内存。

问题三：bss 段如何加载

elf_load_seg 函数对 PT_LOAD 段的处理分两种情况：当 src（文件数据指针）非空时，表示 data 段，从文件拷贝数据到分配的页面；当 src 为空时，表示 bss 段（p_filesz < p_memsz），只通过 map_page 回调分配零填充页面。bss 段在 ELF 文件中不占空间（p_filesz 很小），但加载后会占据 p_memsz 大小的虚拟内存空间，初始值全零。spawn_mapper 中 src == NULL 的分支只调 syscall_mem_alloc 不拷贝，自然得到零页。

Thinking 6.9

标准输入（fd 0）和标准输出（fd 1）是在 user/init.c 中安排的。

流程：icode.b 通过 spawn 创建 init.b。init.b 中调用 opencons() 打开控制台设备，返回的 fd 就是 0（因为它是第一个被打开的 fd）。然后 dup(0, 1) 将 fd 0 复制到 fd 1，使得 fd 1 也指向控制台。之后 init.b 通过 spawn 创建 sh.b，spawn 将父进程所有 PTE_LIBRARY 页面（包括控制台的 fd 页和数据页）映射给子进程。所以 sh.b 继承 fd 0 和 fd 1，分别对应标准输入和标准输出。

Thinking 6.10

MOS 中的 ls.b、cat.b、echo.b、sh.b 等全部是外部命令。

判断依据：MOS shell 的 main 函数对每条命令都先 fork 出子进程，子进程调用 runcmd → spawn 加载对应的 .b 文件执行。没有任何命令由 shell 进程本身直接执行（没有类似”if cmd == ‘cd’ then chdir()”的分支）。

Linux 的 cd 必须是内部命令的原因：cd 修改的是当前进程的工作目录（cwd）。如果 cd 是外部命令，fork 出的子进程会修改子进程自己的 cwd，子进程退出后父进程（shell）的 cwd 不变，命令看起来”没有效果”。因此 cd 必须由 shell 自身直接调用 chdir 系统调用，不能 fork。

Thinking 6.11

以 ls.b | cat.b > motd 为例分析：

spawn 次数：3 次。

  • 第 1 次：shell fork 出的子 shell 进程，在 runcmd 中 spawn("ls.b", ...)，执行管道左侧的 ls 命令。
  • 第 2 次：管道 fork 出的右侧子进程递归调用 parsecmd→runcmd，然后 spawn("cat.b", ...)，执行管道右侧的 cat 命令。
    • cat.b 的 stdout 已通过 > 重定向到文件 motd，所以 cat 的输出写入 motd 而非终端。

进程销毁次数：至少 3 次（对应上述 3 个 spawn 出来的子进程），加上 shell 的 fork 子进程本身和可能的管道 fork 进程，总共在 shell 中可观察到约 5-6 次进程销毁。具体数量取决于 shell 主循环中 fork 的中间进程是否也在 runcmd 中 exit。
