lab4 实验报告

思考题

Thinking 4.1

  • 1.当异常发生时，MIPS CPU 跳转到异常入口。在 kern/entry.S 中，SAVE_ALL 宏负责保存所有通用寄存器到内核栈上的 Trapframe 结构体中。使用 $k0 和 $k1 这两个寄存器作为临时寄存器,SAVE_ALL 将各个寄存器依次存入内核栈。保存完成后，栈指针 $sp 指向 Trapframe 底部，后续 C 代码通过 struct Trapframe *tf 访问所有原始寄存器值。

  • 2.不一定，由于程序不保证一直维护$a0到$a3寄存器的值，可能有些内容需要在栈内预留的空间（Trapframe）读取

  • 3.参数重构。do_syscall 函数充当了”翻译层”：

  • 4.内核修改了两处：
    1. $v0 被改变 → 从内核返回后，syscall_* 函数（以及更上层的 fork、ipc_recv 等）可以通过读取 $v0 获得系统调用的返回值。
    2. EPC + 4 → 返回用户态后，PC 指向 syscall 指令的下一条指令，程序继续正常执行，就像 syscall 是一条普通的函数调用一样。如果不加 4，就会陷入死循环反复执行 syscall。

Thinking 4.2

我们在利用ENVX获取envs数组下标的时候，是直接按后10位索引的，并未判读高位计数器是否一致，如果没有这步判断，由于envs槽位可以复用，可能导致之前希望访问的envid对应的进程已经被回收了，但是我们用相同的下标取出了一个新的存入相同槽位的进程，如果不进行判断，就会错误的进行判断。

Thinking 4.3

我们注意到，即使是第一个进程，由于计数器的自增性质，mkenvid不会返回一个为0的envid。但是envid2env函数中，我们直接将envid与0进行比较，并在envid为0的时候直接将curenv赋给penv，这里实际上我们是将0这个id直接规定为进程自身,系统调用号本身就很紧张，能少传一个参数就少传一个。让envid2env认0等于自己，所有系统调用都可以直接用这个统一的入口，不需要每个系统调用函数里都写一遍”如果 envid是0就换成 curenv”。

Thinking 4.4

选C，fork只被父进程调用了一次，不存在所谓调用两次，A、B、D选项错误，父进程返回子进程的envid，子进程返回0，因此C选项正确。

Thinking 4.5

  • 1.子进程与父进程属于不同的进程，因此一个进程发生异常的时候，不应影响另一进程的运行，因此不能共享异常栈。另外，异常栈本身是异常处理的临时空间，不能在异常处理内部再次出发异常处理，如果使用COW，在进行异常处理的时候，会再次触发TLB Mod异常，导致无限递归死循环。
  • 2.不同进程的页表应当是独立的，否则子进程可能会访问到父进程的物理内存，导致数据混乱。且UVPT映射到的是页表本身，这些数据在父进程和子进程里物理地址不同、内容也不同，
    根本不存在”共享”或”COW”的意义。如果强行 duppage，子进程的 env_pgdir 指针指向子进程自己的页目录物理页，但子进程通过 VPT 读到的却是父进程的页目录，数据完全不一致。

Thinking 4.6

  • 1.vpt指向了该进程所有页表虚拟地址的首地址，vpd指向了该进程页目录虚拟地址的首地址，可以通过vpt + 第n个页表的索引 << 12 + Offset << 2的方式访问对应页表的页表项，通过vpd + Offset << 2的方式访问对应页目录的页目录项。
  • 2.因为实现了页表自映射，所以MMU会自动通过重定向找到对应的页表项的物理地址从而实现修改，且因为页表的虚拟地址放在了用户态的虚拟地址空间，所以用户态程序可以直接访问页表，而不用陷入内核态。
  • 3.这个设计导致了一个递归效果：
    要翻译 UVPT 区域的虚拟地址：
    MMU 第一级查页目录 → 命中自映射 PDE → PDE 指向 PDbase
    → MMU 把第二级也当成页目录来查（而不是页表）
    → 于是原本的”页表项”位置实际读出的是”页目录项”
    → 效果：页目录被当成一个巨大的页表来用
    → 所有页表项在 UVPT 区域连续可见
    这就是”自映射”——页目录的某一个 PDE 的值是自己的物理地址，递归套了一层，使得页表项对用户空间可见。
  • 4.不能，进程对于自己页表的操作权限是只读，不能修改。

Thinking 4.7

  • 1.正常栈 va_X 是 COW 页 → 进程写入 → TLB Mod
    → do_tlb_mod: 保存现场到 UXSTACK(高位)
    → 返回用户态 cow_entry
    cow_entry 执行中:
    → syscall_mem_alloc(0, UCOW, PTE_D) ← UCOW 是新映射的，TLB 里可能没有
    → 访问 UCOW → TLB Miss（不是 TLB Mod，但也走异常）
    → do_tlb_refill: 填 TLB
    → 返回 UCOW 继续
    → memcpy(UCOW, va_X, PGSIZE) ← 读 va_X 正常（COW 只拦截写），写 UCOW 正常（PTE_D=1）
    → syscall_mem_map(…) ← 可能再触发
    如果 cow_entry 处理过程中又碰到另一个 COW 页被写入:
    → 新的 TLB Mod
    → do_tlb_mod: 把当前现场保存到 UXSTACK(低位，比刚才低一个 Trapframe)
    → 再次返回 cow_entry（嵌套）
    → 处理完，syscall_set_trapframe 恢复外层现场
    本质：UXSTACK 上形成 Trapframe 链，每层异常往里压一个，像栈帧一样。 重入的不是”同一个异常”，而是”处理过程中又遇到新的页写入异常”。
  • 2.因为MOS的微内核设计，页面复制和COW处理是在用户态完成的，而用户态无法访问内核空间的Trapframe，因此内核需要复制一份到用户的异常处理栈内。 cow_entry 最后必须调用 syscall_set_trapframe(0, tf) 来恢复现场。这个 tf 指针必须指向用户态能访问的内存，所以内核在 do_tlb_mod 里提前复制到 UXSTACK，用户态 cow_entry 直接拿过来用，最后原样传给内核恢复。

Thinking 4.8

内核更小，运行压力更小。策略灵活， 页写入异常的处理函数存在 env->env_user_tlb_mod_entry 里，该函数是由用户程序自己通过系统调用设的，这意味着不同进程可以用不同的异常处理函数。且fork 本身就在用户态实现的（user/lib/fork.c），COW 处理也是用户态。两层配合不需要跨特权级来回跳。

Thinking 4.9

必须先注册 cow_entry，否则 duppage 自己会把自己炸死。 duppage 遍历的是所有可写用户页，包括 duppage 自身正在跑的栈。设 COW 的过程中把脚下的栈板也锁了，一脚踩下去没有 cow_entry 来救，人就掉下去了。

难点分析

exam难点分析

本次exam考察较为简单的系统调用，主要难点在于熟悉系统调用链路，难度总体不算高

extra难点分析

本次extra难点主要在于对于题目的理解，比如entry为0时取消设置的意思以及后续申请空间与队列填入的先后顺序的问题，由于教程比较详细，除此之外难点并不多。

实验体会

应当加深对于系统调用链路以及kern，user态切换部分的认识。
